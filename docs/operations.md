# Эксплуатация локального стенда

В Фазе 1 доступны API ядра, базовый workflow и Compose для n8n. Прикладные воркеры регистрируются отдельно. Smoke- и benchmark-раннеры указаны ниже как плановые точки входа.

## Каталоги на D:

| Назначение | Путь |
| --- | --- |
| Python venv | `D:\venvs\ai-smartflow-core` |
| Кэши npm, pip и проверок | `D:\cache\ai-smartflow-core\` |
| Базовая папка n8n | `D:\ai-smartflow\n8n` |
| Рабочие БД и резервные копии | `D:\ai-smartflow\data` |
| Временные файлы и отчёты | `D:\ai-smartflow\tmp`, `D:\ai-smartflow\reports` |

Код и локальный `.env` располагаются в подпроекте. Перед запуском проверить доступ на запись, свободное место, версии Node.js и Python по lock-файлам будущего стенда и отсутствие занятых портов. Переиспользовать постоянный ключ шифрования n8n и хранить его отдельно от состояния и резервных копий.

## n8n

Из корня подпроекта создай папку `D:/ai-smartflow/n8n/.n8n` и выполни `docker compose -f infra/docker-compose.yml up -d`. Compose публикует порт на loopback хоста и монтирует workflow в `/workflows` для импорта. Импортируй `workflows/_base/base_smartflow_template.json` из редактора n8n и назначь Header Auth для входящего Webhook и обоих HTTP Request. Для запросов в ядро имя заголовка — `X-Smartflow-Token`, значение — `WORKER_TOKEN`. Для входящего Webhook используй отдельный секрет.

В шаблон передаётся зарегистрированный `WorkerRequestEnvelope`. Вызов `POST /v1/deliveries` доверенным адаптером выдаёт контекст доставки. После успешного результата разрешающая политика или обработчик подтверждённого решения сохраняет команду через `Journal.approve`. При первом вызове до апрува диспетчер возвращает HTTP 409. После апрува повтор с тем же конвертом использует сохранённый результат и запускает публикацию. Для результата с `need_human=true` шаблон отдаёт ответ на ручную проверку. Ручное возобновление вызывает диспетчер отдельно после подтверждения конкретной ревизии. Узел `Wait 600ms` регулирует один маршрут. Общий лимит обеспечивает один процесс диспетчера на портал.

В Docker Desktop HTTP-узлы используют `host.docker.internal:8021`. Проверь его доступность из контейнера. Если локальная конфигурация Docker не маршрутизирует loopback хоста, используй нативный n8n и задай адрес обоих HTTP-узлов `127.0.0.1:8021`.

Для нативного запуска используй PowerShell. В PowerShell перед запуском создать указанные ниже каталоги, задать переменные в сессии и подставить утверждённую версию вместо `<version>`.

```powershell
$env:N8N_HOST = '127.0.0.1'
$env:N8N_LISTEN_ADDRESS = '127.0.0.1'
$env:N8N_PORT = '5678'
$env:N8N_USER_FOLDER = 'D:\ai-smartflow\n8n'
$env:npm_config_cache = 'D:\cache\ai-smartflow-core\npm'
$env:TEMP = 'D:\ai-smartflow\tmp'
$env:TMP = $env:TEMP
npx --yes 'n8n@<version>' start
```

Открыть `http://127.0.0.1:5678`. Импортировать базовый workflow, привязать локальные credentials и активировать после проверки с заглушками. Для исходящих вызовов Bitrix24 используется общая очередь портала. Входы локального smoke — синтетические события. При подключении живого портала локальный профиль опрашивает его исходящими запросами. Публикация входящего webhook за пределами loopback требует отдельной настройки ingress.

[Npm-установка n8n](https://docs.n8n.io/hosting/installation/npm/) · [Переменные n8n](https://docs.n8n.io/hosting/configuration/environment-variables/deployment/)

## FastAPI

Плановые адреса — `127.0.0.1:8021` и далее. Закрепить порт каждого процесса в конфигурации n8n. Создать venv и кэши на `D:\`. Значения кэшей из `.env.example` для pip и Python устанавливаются в PowerShell до запуска инструмента. Директории кэшей Ruff, Mypy и pytest заданы в `pyproject.toml`. Запускать из корня подпроекта:

```powershell
$cache = 'D:/cache/ai-smartflow-core'
New-Item -ItemType Directory -Force -Path "$cache/pip", "$cache/tmp", "$cache/pycache" | Out-Null
$env:PIP_CACHE_DIR = "$cache/pip"
$env:PYTHONPYCACHEPREFIX = "$cache/pycache"
$env:TEMP = "$cache/tmp"
$env:TMP = $env:TEMP
py -3 -m venv D:/venvs/ai-smartflow-core
& 'D:/venvs/ai-smartflow-core/Scripts/Activate.ps1'
python -m pip install -e '.[dev]'
python -m uvicorn core.api:app_factory --factory --host 127.0.0.1 --port 8021
```

`app_factory` запускает API журнала и диспетчер для заданного webhook Bitrix24. Прикладная точка входа передаёт воркеры в `create_app`. При нескольких воркерах закрепить за процессами отдельные порты. Диспетчер с полномочиями CRM запускается в одном процессе на портал. Настроить `BASE_URL`, ключ, три модели, доверенные профили и путь к SQLite. Preflight проверяет `GET /health` на каждом порту, миграции, WAL, FK, читаемость активного профиля и достижимость воркера из n8n. SQLite ядра и база состояния n8n хранятся раздельно. Для резервирования использовать SQLite backup API либо согласованную офлайн-копию после остановки процессов и контрольной точки WAL.

## Smoke и benchmark

Плановые CLI после сборки ядра, с активированным venv:

```powershell
python -m ops.runners.smoke_runner --dry-run
python -m ops.runners.benchmark_runner --mode dry-run
```

- Dry-run изолирует SQLite и подменяет LLM и Bitrix24. Smoke проходит S1→S2→S3 на тестовых payload, проверяет дубли, ручную паузу, частичную публикацию и сверку незавершённого шага.
- Benchmark использует 50–100 размеченных сценариев, в том числе шум, пропуски, повторы и ошибки внешних вызовов. Парный A/B использует одинаковые входы с раздельными ключами доставки. Отчёт указывает объём выборки, версии, p50/p95 времени цикла, долю эскалаций, ошибки, токены, стоимость и полноту замеров.
- `--live-llm` для smoke и `--mode live-llm` для benchmark включают реальные расходы на LLM в пределах настроенного бюджета. CRM остаётся подменённой. Отдельный интеграционный прогон на тестовом портале проверяет scopes, связи, чтение по внешнему ключу и лимитер.
- По завершении сохранить отчёт на `D:\`, внести фактические результаты и открытые дефекты в [срез состояния](status.md). При `reconcile` сопоставить внешние ID и метки согласно [контракту](contracts.md), оформить решение в журнале и возобновить только подтверждённый переход.

## S1.3 · Тестовый портал и n8n

В корне подпроекта выполни `python -m ops.runners.b24_setup_s1` для проверки
настроек и `python -m ops.runners.b24_setup_s1 --apply` для добавления недостающих
объектов тестового портала. Утилита читает `BITRIX24_WEBHOOK_URL` из окружения,
проверяет `method.get` и использует общий ограничитель BitrixClient.
Запускай утилиту отдельно от FastAPI, чтобы не делить квоту между процессами.
После неопределённого ответа проверь портал повторным прогоном без `--apply`.

Для S1.4 импортируй оба JSON в n8n 2.48.5. Привяжи Header Auth к входящему
webhook заявки, к webhook реестров и его HTTP-клиенту, а к HTTP-узлам ядра
привяжи Header Auth с заголовком `X-Smartflow-Token` из `WORKER_TOKEN`.
Учётные данные назначаются в n8n. После настройки тестового контура запусти
сначала webhook реестров, затем onboarding. Оба экспорта импортируются неактивными.

Адрес заявки `POST /webhook/s1-kyc-onboarding`. JSON содержит `delivery_key`,
`source_type` и ровно один из `text` и `pdf_base64`. Поле `scenario` принимает
`green`, `arbitration`, `bankruptcy`, `timeout`. Workflow фиксирует рабочий
профиль `portal_b24_b2b` ревизии `3` и `run_origin=mock`.
Публикация после активации использует указанный в профиле тестовый портал.
Для смены ревизии обнови профиль и узел нормализации заявки вместе.

## S1.4 · Воспроизведение приёмки

Запускай из корня подпроекта в новом каталоге отчёта на D:.

```powershell
python -m ops.runners.benchmark_s1 --output D:/ai-smartflow/reports/s14-benchmark-new
python -m ops.runners.smoke_live_s1 --output D:/ai-smartflow/reports/s14-pilot-new
```

Benchmark использует 35 размеченных входов на профиль и записывает SQLite и JSON-отчёт.
Живой раннер создаёт две карточки тестового портала, проверяет повтор, комментарии и
допуск в S2, затем останавливает временный FastAPI. Повтор запуска с новым каталогом
создаёт новую пару карточек. При транспортном сбое сначала проверь состояние журнала
прошлого прогона. При проблеме DNS параметр `--pin-ip` задаёт проверенный IP портала
внутри процесса. Имя хоста и проверка TLS сохраняются.
