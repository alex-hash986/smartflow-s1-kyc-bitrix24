# Контракты ядра · v1

Нормативная спецификация к [ADR-001](ARCHITECTURE_DECISION_RECORD.md). Примеры описывают будущую реализацию.

## WorkerRequestEnvelope и WorkerResponseEnvelope

n8n вызывает `POST /v1/workers/{stage}/run` по HTTP JSON. Все перечисленные поля обязательны. `null` допускается только там, где указан. Для обоих конвертов и вложенных моделей применяется Pydantic v2 с `model_config = ConfigDict(extra="forbid")`. Проверяются типы JSON без неоговорённых преобразований. Прикладная схема `payload` определяется направлением, этапом и версией протокола. В пределах версии её идентифицирует закреплённая ревизия профиля.

| Поле | Вход | Выход | Тип и смысл |
| --- | --- | --- | --- |
| `schema_version` | ✓ | ✓ | Строка `"1"` |
| `tenant_id` | ✓ | ✓ | Непустой ID доверенного тенанта |
| `request_id` | ✓ | ✓ | UUID общего цикла S1→S2→S3 |
| `profile_slug`, `profile_revision` | ✓ | ✓ | Непустые строки закреплённого профиля |
| `stage` | ✓ | ✓ | `S1`, `S2` или `S3`, совпадает с путём |
| `attempt` | ✓ | ✓ | Целое ≥ 1, выдаётся ядром для попытки этапа |
| `received_at` | ✓ | | RFC 3339 с поясом, нормализация в UTC |
| `upstream_item` | ✓ | | `null` для S1, иначе `{entity_type_id, item_id}` с положительными целыми ID подтверждённой карточки предыдущего этапа |
| `payload` | ✓ | ✓ | Объект по прикладной схеме. В ответе допустим `null` только при эскалации |
| `need_human` | | ✓ | Boolean |
| `escalation_reasons` | | ✓ | Массив кодов профиля или ядра, непустой ровно при `need_human=true` |
| `cost_rub` | | ✓ | Неотрицательная десятичная строка с восемью дробными знаками или `null` |
| `mode` | | ✓ | `llm`, `deterministic` или `fallback` |
| `fallback_reason` | | ✓ | Непустой стабильный код при `mode=fallback`, иначе `null` |

Ответ повторяет корреляционные поля входа. `deterministic` означает запланированный расчёт без LLM. `fallback` фиксирует переключение после сбоя, превышения бюджета или нехватки подтверждённых данных. Если безопасного результата нет, выставляется `need_human=true` и блокируется обычная публикация до подтверждённого решения по ревизии. Успешная обработка и бизнес-эскалация возвращают HTTP 200. Неверный конверт даёт 422, конфликт содержимого для той же попытки — 409, временная недоступность — 503. Сбой транспорта не считается бизнес-результатом.

Повтор вызова с тем же `(tenant_id, request_id, stage, attempt)` получает сохранённый ответ или статус уже выполняющейся попытки (202 с `Retry-After`). Ядро атомарно резервирует попытку и сохраняет входной хэш до вычисления. Новую попытку выдаёт ядро после завершения или признания прежней прерванной. Устаревший исполнитель не может сохранить результат поверх новой попытки. Приём результата и постановка следующего действия фиксируются в журнале до подтверждения n8n. Воркеры используют внутреннюю сервисную аутентификацию и не имеют полномочий записи в Bitrix24.

Бизнес-суммы передаются десятичными строками. `Decimal` округляется через `quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)` в согласованной точке расчёта. Себестоимость всех вызовов накапливается в Decimal и квантуется до `0.00000001` на уровне отчётной записи. В SQLite `cost_rub_e8` хранит целое количество стомиллионных долей рубля. Переполнение signed 64-bit отклоняется. `NULL` означает неизвестную полную стоимость, ноль — подтверждённое отсутствие расхода.

## SQLite WAL

Применить WAL к файлу на локальном диске и проверить результат `wal`. Включать FK и timeout для каждого соединения. UUID и даты пишутся в каноническом текстовом виде, метки времени — в UTC. Во всех чтениях и изменениях обязательна область `tenant_id`. JSON ниже сериализуется приложением и проверяется по схеме перед записью или повторным использованием.

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;

CREATE TABLE idempotency_records (
    tenant_id TEXT NOT NULL,
    source TEXT NOT NULL,
    delivery_key TEXT NOT NULL,
    input_sha256 TEXT NOT NULL CHECK (length(input_sha256) = 64),
    input_json TEXT NOT NULL,
    request_id TEXT NOT NULL,
    profile_slug TEXT NOT NULL,
    profile_revision TEXT NOT NULL,
    received_at TEXT NOT NULL,
    PRIMARY KEY (tenant_id, source, delivery_key),
    UNIQUE (tenant_id, request_id)
) STRICT;

CREATE TABLE transaction_telemetry (
    tenant_id TEXT NOT NULL,
    request_id TEXT NOT NULL,
    processing_time_sec REAL CHECK (processing_time_sec >= 0),
    tokens_in INTEGER CHECK (tokens_in >= 0),
    tokens_out INTEGER CHECK (tokens_out >= 0),
    cost_rub_e8 INTEGER CHECK (cost_rub_e8 >= 0),
    mode TEXT CHECK (mode IN ('llm', 'deterministic', 'fallback')),
    fallback_reason TEXT,
    ab_variant TEXT,
    channel TEXT NOT NULL,
    is_after_hours INTEGER NOT NULL CHECK (is_after_hours IN (0, 1)),
    need_human INTEGER CHECK (need_human IN (0, 1)),
    saved_minutes REAL,
    run_origin TEXT NOT NULL CHECK (run_origin IN ('mock', 'benchmark', 'pilot')),
    outcome TEXT NOT NULL CHECK (outcome IN ('running', 'waiting_human', 'completed', 'failed', 'reconcile')),
    updated_at TEXT NOT NULL,
    PRIMARY KEY (tenant_id, request_id),
    FOREIGN KEY (tenant_id, request_id) REFERENCES idempotency_records (tenant_id, request_id),
    CHECK (CASE WHEN mode = 'fallback'
        THEN fallback_reason IS NOT NULL AND length(fallback_reason) > 0
        ELSE fallback_reason IS NULL END)
) STRICT;

CREATE TABLE transaction_stages (
    tenant_id TEXT NOT NULL,
    request_id TEXT NOT NULL,
    stage TEXT NOT NULL CHECK (stage IN ('S1', 'S2', 'S3')),
    attempt INTEGER NOT NULL CHECK (attempt > 0),
    status TEXT NOT NULL CHECK (status IN ('running', 'completed', 'failed', 'interrupted')),
    input_sha256 TEXT NOT NULL CHECK (length(input_sha256) = 64),
    response_json TEXT,
    started_at TEXT NOT NULL,
    finished_at TEXT,
    error_code TEXT,
    mode TEXT CHECK (mode IN ('llm', 'deterministic', 'fallback')),
    fallback_reason TEXT,
    prompt_versions_json TEXT,
    tokens_in INTEGER CHECK (tokens_in >= 0),
    tokens_out INTEGER CHECK (tokens_out >= 0),
    cost_rub_e8 INTEGER CHECK (cost_rub_e8 >= 0),
    PRIMARY KEY (tenant_id, request_id, stage, attempt),
    FOREIGN KEY (tenant_id, request_id) REFERENCES transaction_telemetry (tenant_id, request_id),
    CHECK (status <> 'completed' OR (response_json IS NOT NULL AND mode IS NOT NULL)),
    CHECK (CASE WHEN mode = 'fallback'
        THEN fallback_reason IS NOT NULL AND length(fallback_reason) > 0
        ELSE fallback_reason IS NULL END)
) STRICT;

CREATE UNIQUE INDEX one_running_attempt
    ON transaction_stages (tenant_id, request_id, stage) WHERE status = 'running';

CREATE TABLE crm_publications (
    tenant_id TEXT NOT NULL,
    request_id TEXT NOT NULL,
    stage TEXT NOT NULL,
    stage_attempt INTEGER NOT NULL,
    purpose TEXT NOT NULL CHECK (purpose IN ('stage_result', 'human_review')),
    portal_id TEXT NOT NULL,
    external_key TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('approved', 'publishing', 'published', 'reconcile')),
    approved_at TEXT NOT NULL,
    approval_ref TEXT NOT NULL,
    command_json TEXT NOT NULL,
    owner_token TEXT,
    entity_type_id INTEGER NOT NULL CHECK (entity_type_id > 0),
    item_id INTEGER CHECK (item_id > 0),
    task_required INTEGER NOT NULL CHECK (task_required IN (0, 1)),
    task_id INTEGER CHECK (task_id > 0),
    pending_step TEXT CHECK (pending_step IN ('item', 'task')),
    updated_at TEXT NOT NULL,
    PRIMARY KEY (tenant_id, request_id, stage, purpose),
    UNIQUE (portal_id, external_key),
    FOREIGN KEY (tenant_id, request_id, stage, stage_attempt)
        REFERENCES transaction_stages (tenant_id, request_id, stage, attempt),
    CHECK (status <> 'publishing' OR owner_token IS NOT NULL),
    CHECK (status <> 'published' OR
        (pending_step IS NULL AND item_id IS NOT NULL AND (task_required = 0 OR task_id IS NOT NULL)))
) STRICT;
```

Регистрация доставки и начальная строка телеметрии создаются в одной транзакции. `source` идентифицирует доверенный канал и источник. `delivery_key` — стабильный ID исходного события или ключ из нормализованных неизменяемых бизнес-полей, предусмотренный адаптером. `input_sha256` вычисляется по каноническому нормализованному входу без метаданных доставки. При конфликте ключа сравнить хэш и вернуть сохранённые ID, профиль и время при совпадении или 409 при расхождении. Последующие события подтверждения привязываются к исходному циклу и ревизии. Повтор решения условно применяет тот же переход, включая после перезапуска.

## Публикация и восстановление

1. Ядро сохраняет `approved` с неизменяемой командой, закреплённой попыткой и ссылкой на решение человека или версию разрешающей политики. На этап приходится по одной публикации каждого назначения. Правки опубликованной карточки требуют отдельного контракта. Задача на проверку привязывается к существующей карточке или карточке очереди проверки, разрешённой профилем. Она не открывает следующий этап. В S1 при `tasks_enabled: false` очередь состоит из карточки в стадии проверки и комментария таймлайна.
2. Диспетчер n8n получает разрешение только через условный `UPDATE ... WHERE status = 'approved'`, который в короткой транзакции назначает `owner_token` и переводит строку в `publishing`. Ноль изменённых строк запрещает внешний вызов. Все дальнейшие записи исполнителя проверяют токен и статус. Сетевые вызовы выполняются после коммита.
3. Перед каждым внешним изменением сохранить `pending_step`. После подтверждённого успеха атомарно сохранить ID и очистить `pending_step`. После всех обязательных действий установить `published`. Восстановление использует сохранённые ID, сверяет принадлежность и связи и выполняет только отсутствующие шаги.
4. При тайм-ауте записи, разрыве соединения, неопределённом 5xx или сбое между записью в CRM и сохранением ID перевести операцию в `reconcile`. Истечение тайм-аута исполнителя само по себе не разрешает новому исполнителю отправить запись. До возобновления исключить активность прежнего исполнителя и сверить неизвестный шаг в Bitrix24. Один достоверно совпавший объект позволяет сохранить его ID. Ноль результатов при неопределённом исходе, несколько объектов или неполный доступ требуют ручной сверки. Повтор записи разрешается только при подтверждённом отсутствии эффекта и завершённой исходной попытке. Решение и новый захват фиксируются в журнале, успешные шаги сохраняются.
5. `published` для `stage_result` и подтверждённая ссылка на карточку открывают следующий этап. Повторные уведомления не запускают новую попытку уже завершённого этапа. Интеграция обеспечивает локальный атомарный захват с восстановлением и сверкой внешнего эффекта.

## Интеграция n8n ↔ Bitrix24

- Базовый профиль использует совместимый REST с правами `crm` для Смарт-процессов и `task` для задач. Отдельные credentials на контур хранятся в n8n. Для входящих уведомлений проверять подлинность, доверенный портал и актуальное состояние карточки. Локальный режим использует polling или синтетические события.
- Профиль закрепляет `portal_id`, `entityTypeId`, категорию, стадии, поле внешнего ключа, поле связи с предыдущей карточкой и ответственного. Методы `crm.item.add/get/list/update` работают с `entityTypeId` и ID карточки. Обновления из других интеграций требуют проверки согласованности профиля и ревизии. Перед запуском подтвердить наличие методов, полей и прав на тестовом портале.
- Для `tasks.task.add` передать `fields.TITLE`, `fields.RESPONSIBLE_ID` и `fields.UF_CRM_TASK` как массив строк. Привязка Смарт-процесса имеет вид `T{hex(entityTypeId)}_{itemId}`: lowercase hex без `0x`, ID карточки в десятичном виде. Например, тип 177 и ID 29 дают `["Tb1_29"]`. Считать ID из `result.task.id` и проверить привязку чтением задачи.
- Внешний ключ вычисляется из канонического кортежа `(tenant_id, request_id, stage, purpose)`, например SHA-256. Записывать его в согласованное поле карточки и как однозначную метку задачи. Для задачи совпадение проверяется по метке и привязке. При использовании существующей карточки её ID закрепляется в команде. Поиск проверяет весь набор страниц, точное совпадение и область портала.
- Общий лимит по порталу — **≤ 2 запроса/с**, интервал между отправками ≥ 500 мс, без всплесков. Единая очередь отправки объединяет workflow, пагинацию, сверку и повторы. Пакетные вызовы для обхода лимита отключены. Для временных ограничений учитывать `Retry-After` при наличии, применять ограниченный backoff с jitter и учитывать коды ошибок REST в теле. Безопасные чтения можно повторять. Запись после неоднозначной ошибки следует протоколу сверки.

## Телеметрия и шлюз моделей

- Фиксировать попытки, ошибки, версии промптов и usage по этапам. Токены и стоимость цикла включают повторы. Если часть фактического расхода неизвестна, итог этой метрики равен `NULL`. Фолбэк обязательного этапа становится режимом цикла с первой причиной по порядку событий. Иначе при наличии LLM-вызова режим цикла `llm`, для полностью детерминированного маршрута — `deterministic`. До появления измерения режим может оставаться неизвестным.
- Время цикла считаётся от приёма доставки до завершения последней публикации или фиксации терминального сбоя. Оно включает ожидания и паузы человека. Для длительностей внутри попытки используются монотонные часы, для сквозного цикла с перезапусками — сохранённые метки UTC. Рабочие часы определяются по календарю тенанта на момент приёма. `saved_minutes` основан на сопоставимых замерах активного труда и допускает отрицательное значение.
- Единый OpenAI-совместимый шлюз читает `BASE_URL`, `API_KEY`, `FAST_LLM_MODEL`, `SMART_LLM_MODEL`, `EMBEDDING_MODEL` из конфигурации. Для структурированного чата включает `response_format={"type":"json_object"}`. Индекс закрепляет модель, размерность и ревизию эмбеддингов. Расход считается по версии тарифа и использованному курсу с контролем бюджета перед вызовом.


## Контракты модуля `s1_kyc` (Кейс S1)

### Границы этапа

n8n принимает заявку, передаёт текст или PDF на извлечение, запрашивает реестры по проверенным реквизитам и собирает нормализованный снимок. FastAPI валидирует его и рассчитывает решение по закреплённой ревизии профиля. Bitrix24 хранит опубликованное решение и результат ручной проверки.

Сначала n8n регистрирует доставку через `POST /v1/deliveries`. Внутренние маршруты S1 используют заголовок `X-Smartflow-Token` и поля `tenant_id`, `request_id`, `profile_slug`, `profile_revision` зарегистрированной доставки.

- `POST /s1/parse` принимает этот контекст и `payload: S1ParseRequest`. Ответ возвращает контекст, `payload: S1ParseResponse`, `mode`, `fallback_reason`, `cost_rub` и `prompt_version`. Повтор того же источника возвращает сохранённый ответ, параллельный повтор получает 202 с `Retry-After`, изменение источника в том же цикле даёт 409. Журнал `s1_extractions` закрепляет хэш, ответ и расход. При аварийном завершении процесса незакрытая запись требует операционной сверки перед возобновлением, поскольку расход может быть неизвестен.
- `POST /s1/evaluate` принимает тот же контекст, `attempt`, `received_at` из квитанции доставки и `payload: S1EvaluateRequest`. Маршрут использует тот же журнал попыток, что и `POST /v1/workers/S1/run`. Оба возвращают `WorkerResponseEnvelope` с бизнес-полями `S1EvaluateResponse` в `payload` и общими метаданными во внешнем конверте.

### Общие правила DTO

Все модели и вложенные объекты используют Pydantic v2 и `model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)`. Поля обязательны, в том числе явно nullable. Для строк, целых и boolean используются строгие типы. На границе JSON для Decimal принимаются только десятичные строки с точкой без знака, экспоненты и разделителей групп. Рубли и баллы сериализуются с двумя дробными знаками, себестоимость — с восемью. Валидатор отклоняет лишние дробные знаки, а расчёт квантует результат по общему стандарту. Коды причин уникальны и отсортированы. `need_human` истинно ровно при непустом `escalation_reasons`.

### Извлечение

| DTO | Поле | Тип и ограничения |
| --- | --- | --- |
| `S1ParseRequest` | `source_type` | `TEXT \| PDF` |
| | `text` | Строка или null. Для TEXT передаётся строка. Пустой текст ведёт к ручной проверке |
| | `pdf_base64` | Строгий base64 без пробелов внутри или null. Заполнено для PDF. После декодирования проверяются формат PDF и лимит размера из профиля |
| `S1ParseResponse` | `inn`, `ogrn`, `kpp` | Строки ASCII-цифр или null. ЮЛ: ИНН 10, ОГРН 13, КПП 9 цифр. ИП: ИНН 12, ОГРНИП 15 в поле `ogrn`, КПП null. Для ИНН, ОГРН и ОГРНИП обязательны контрольные цифры |
| | `legal_name` | Непустая строка или null |
| | `requested_limit_rub` | Decimal > 0 или null |
| | `need_human`, `escalation_reasons` | Boolean и список кодов из профиля |

S1 обслуживает российские ЮЛ и ИП. Извлечение возвращает null для отсутствующих, неоднозначных или невалидных реквизитов с кодом причины. КПП для ИП неприменим. При эскалации n8n ждёт подтверждённые реквизиты до запроса реестров и запуска оценки. При неполном читаемом тексте возможен вызов FAST LLM с бюджетом цикла. Пустой скан без текстового слоя передаётся человеку. Детерминированная проверка реквизитов обязательна в любом режиме.

| | `fns_address_unreliable`, `bankruptcy` | Boolean или null |
| | `observed_at` | RFC 3339 с поясом, нормализуется в UTC |
| `S1EvaluateRequest` | `parsed` | `S1ParseResponse` с `need_human=false` и всеми применимыми реквизитами |
| | `registry` | `S1RegistrySnapshot` с теми же ИНН и ОГРН |
| `S1EvaluateResponse` | `reliability_score` | Decimal от `0.00` до `100.00` включительно или null при неполном либо просроченном снимке |
| | `risk_level` | `LOW \| MEDIUM \| HIGH \| CRITICAL` или null одновременно с баллом |
| | `recommended_credit_limit_rub` | Decimal ≥ 0. Верхняя граница равна запрошенному лимиту |
| | `payment_terms` | Объект с `kind` = `PREPAYMENT \| DEFERRED` и целым `deferment_days`. Предоплата соответствует нулю дней и нулевому лимиту. Отсрочка требует положительных дней и лимита |
| | `stop_factors` | Список обнаруженных стоп-факторов из профиля, уникальный и отсортированный |
| | `dossier_markdown` | Непустая строка с фактами, расчётом или причиной его отсутствия и рекомендацией |
| | `need_human`, `escalation_reasons` | Boolean и список кодов. В Worker API берутся из конверта |
| | `cost_rub`, `mode`, `fallback_reason` | По общему конверту. В Worker API берутся из конверта |

`null` в снимке означает неподтверждённое значение. Ноль и false допустимы только как подтверждённые значения. При недоступности реестров n8n передаёт снимок с null для неизвестных показателей. Возраст снимка отсчитывается от времени самого раннего подтверждённого наблюдения. Если ни одного наблюдения нет, `observed_at` фиксирует завершение сбора. Снимок из будущего отклоняется, снимок старше лимита профиля эскалируется. Просроченный снимок не используется для определения стоп-факторов. Досье формируется детерминированно. Режим оценки `deterministic` при полном снимке и `fallback` при неполном или просроченном снимке, с причиной `REGISTRY_INCOMPLETE` или `REGISTRY_STALE`. Расход самой оценки равен `0.00000000`. Расход извлечения учитывается в телеметрии цикла отдельно, один раз на фактическое выполнение.

С полным актуальным снимком балл равен 100 минус сумма применимых штрафов, с ограничением снизу нулём. Порог применяется включительно. Условия штрафов по возрасту используют строгое сравнение ниже порога, по суммам исков и долга — выше порога. Оба штрафа по сумме исков могут суммироваться. Уровень выбирается по наибольшей пройденной нижней границе. Стоп-фактор при полном снимке принудительно задаёт CRITICAL. При стоп-факторе, неполном или просроченном снимке, либо риске из списка ручной проверки устанавливаются эскалация, предоплата и нулевой лимит. Коды причин включают обнаруженные стоп-факторы и применимые коды данных и риска. Иначе лимит равен меньшему из запрошенной суммы и потолка профиля для уровня риска. Положительный лимит даёт отсрочку на срок из профиля.

### Публикация карточки Bitrix24 «Проверка контрагента»

Ключи ниже — логические имена. Ревизия профиля связывает их с физическими кодами полей, типом Смарт-процесса и значениями перечисления портала. При публикации `stage_result` все пять полей обязательны в одной команде. Рекомендованный лимит становится утверждённым по применимой политике или по сохранённому решению человека.

| Ключ | Тип поля | Публикуемое значение |
| --- | --- | --- |
| `INN` | Строка | Подтверждённый ИНН ЮЛ, 10 цифр, или ИП, 12 цифр |
| `OGRN` | Строка | Подтверждённый ОГРН ЮЛ, 13 цифр, или ОГРНИП, 15 цифр |
| `KYC_STATUS` | Одиночное перечисление | `APPROVED` либо `REJECTED`, через маппинг ID значений |
| `RELIABILITY_SCORE` | Строка | Каноническое представление Decimal с двумя знаками |
| `APPROVED_CREDIT_LIMIT_RUB` | Строка | Каноническое представление Decimal в рублях с двумя знаками. При отказе — `0.00` |

При ручной проверке без рассчитанного балла решение о финальной публикации требует дополнить снимок и повторить оценку. Запись `human_review` служит очередью проверки. Для S1 → S2 действуют общий протокол `published`, подтверждённая ссылка и дополнительный шлюз `KYC_STATUS=APPROVED`. n8n читает связанную карточку и проверяет типы, допустимость значений и совпадение реквизитов с утверждённой попыткой. При несоответствии требуется сверка. `REJECTED` завершает маршрут.

### Профили и реализация

Шаблоны `profiles/*/profile.yaml` закрепляют параметры извлечения, правила оценки и контракт привязки к Bitrix24. Суммы и границы баллов в YAML задаются строками. Правила сравнения используют `lt` (<), `gt` (>), `eq` (=) и `ne` (≠). Пороги и лимиты шаблонов — стартовые параметры для ревью и проверки на данных пилота. Версия профиля закрепляется на весь цикл. Значения портальных привязок требуют настройки и проверки по тестовому порталу. Загрузчик валидирует секцию `s1_kyc`. `template: true` разрешает незаполненные портальные привязки для расчёта. Для публикации на S1.3 задаются реальные привязки, `template: false` и новая ревизия профиля. Структура файлов и их ответственность закреплены в [каркасе модуля](../modules/s1_kyc/README.md).

### Воркфлоу S1 с учебными реестрами

`POST /s1/publication/prepare` принимает корреляцию S1 и номер попытки. Сервис читает
сохранённые результаты и строит команду из рабочего профиля. Входящий webhook
не задаёт CRM-поля, стадию или решение. Правило `policy:s1-mock:<slug>:<revision>`
действует только для записей с `run_origin=mock`. При эскалации извлечения
ядро фиксирует завершённую попытку S1 без оценки, чтобы закрепить очередь проверки
за сохранённым результатом извлечения.

Для результата без эскалации политика mock публикует `stage_result` со статусом
`APPROVED`. Для эскалации публикуется `human_review` в стадии СБ, с доступными
реквизитами, досье и задачей только при `s1_kyc.bitrix24.tasks_enabled: true`.
Финальный статус KYC и утверждённый лимит в такой карточке остаются пустыми.

Диспетчер ищет точное совпадение `EXTERNAL_KEY`, сверяет ИНН при его наличии
и может обновить только карточку с тем же внешним ключом. ИНН сам по себе
не связывает независимые заявки. Досье записывается через `crm.timeline.comment.add`.
`crm_publication_comments` хранит незавершённый шаг и ID комментария.
При неопределённом ответе проверь таймлайн карточки по метке `[smartflow:<key>]`.
Команда сверки фиксирует подтверждённый ID шага `comment` или подтверждённое
отсутствие записи. Успешные шаги не повторяются.
